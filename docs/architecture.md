# Как устроена Persona

## Контекст владельца

Obsidian и папка проектов индексируются с отслеживанием изменений и версиями документов. Обновления попадают в очередь переиндексации. Источники vault и code подключены для чтения: этот путь не записывает изменения в исходные файлы. Документы Google Drive синхронизируются отдельно, включая изменения и удаления поддерживаемых файлов.

Gmail читается в момент запроса: поиск возвращает метаданные, snippet и ссылку на письмо. Полное тело письма в этом поиске не запрашивается, письма не попадают в поисковый индекс. Google-инструменты доступны после подключения соответствующей интеграции.

## Поиск и ответ

1. SQL ограничивает документы по правам пользователя.
2. Полнотекстовый поиск на русском и английском выполняется вместе с векторным поиском pgvector.
3. Ранжированные списки объединяются через Reciprocal Rank Fusion; для вариантов запроса предусмотрен weighted RRF.
4. Дополнительные шаги — переформулирование вопроса, реранк и объединение соседних фрагментов.
5. Модель получает найденные материалы. Ответ передаёт источники в интерфейс, а номера цитат проходят проверку.

Если RAG не нашёл материалов, предусмотрен явный `not_found`. Проверка номера цитаты подтверждает наличие ссылки в ответе, а не истинность произвольного утверждения.

Эмбеддинги bge-m3 (1024 измерения) выполняются локально в Ollama. В конфигурации предусмотрены внешние провайдеры для генерации, реранка и распознавания речи.

## Агент и действия

LangGraph связывает планирование и инструменты. Предложение чат-агента о записи сначала становится карточкой, затем выполнение приостанавливается через `interrupt`. После решения владельца доступность инструмента проверяется повторно. PostgreSQL checkpointer хранит состояние ожидающего решения.

Это правило относится к предложениям агента. Прямые действия пользователя и заранее разрешённые автоматизации имеют отдельные пути; например, правило может разрешить отправку автоматического напоминания без решения на каждый запуск.

MCP-сервер предоставляет инструменты внешним клиентам. Доступные через MCP операции записи создают заявки на подтверждение, а не выполняют изменение сразу.

## Отдельные агентские сессии

- Чтение локальных файлов: Read/Grep/Glob, проверка путей, без shell, записи, веба и MCP.
- Веб-исследование: WebSearch/WebFetch, без файловых инструментов.
- Многошаговое исследование: подвопросы, ограничение времени и шагов, параллельный сбор материала, итоговый отчёт и SSE-прогресс.

Разделение инструментов не означает, что данные никогда не покидают сервер: текст вопроса и материалы для ответа могут передаваться выбранным внешним моделям.

## Ошибки и наблюдаемость

У модельных задач есть настраиваемые цепочки провайдеров и учёт лимитов. Ошибка до начала ответа позволяет перейти к следующему провайдеру. Обрыв уже начавшегося потока завершает ответ с сообщением об ошибке, а не подменяет модель посередине.

Для исследования предусмотрены частичные результаты. Незавершённые задания распознавания аудио восстанавливаются после перезапуска с ограничением числа попыток.

Аудит хранится в PostgreSQL с цепочкой хэшей и отдельным подписантом якорей. JSON-логи связаны через `trace_id`; предусмотрена интеграция Langfuse.

## Границы текущего описания

Описана реализация персонального режима. В закрытой кодовой базе остаются части корпоративного прототипа; оргграф сотрудников, Битрикс24/1С и корпоративные дашборды не заявляются как возможности Persona One.

Документ составлен по чтению реализации. Он не является отчётом о пройденном полном тестировании или подтверждением готового запуска на чистом клоне.
